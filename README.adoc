= OpenShift 102 Workshop

Antora showroom site for the OpenShift 102 workshops: Helm, advanced deployment, Istio, and Prometheus.
All four live in this repository and are published together as one site and one PDF.

== Workshops

Each workshop is its own Antora component under `workshops/`, so the four keep their own navigation and URLs inside the one site.
The hub pages (start page and the shared CLI tools page) are in `content/openshift-102/`, together with the site's Antora extensions (`lib/`), which all four workshops share.
The site's look (theme, CSS, tabs, copy buttons, footer) and the Pages and PDF test workflows come from https://github.com/shpwrck/workshop-common[workshop-common], which the other workshop repos share too; change them there.

Each workshop's `antora.yml` names the component (`helm-workshop`, `deploy-workshop`, and so on) and holds its AsciiDoc attributes; `nav.adoc` under `modules/ROOT/` sets its page order.
The four workshops used to be separate repositories pulled in as Git submodules; they were folded in here so there is one repository to maintain.

== Workshop CLI tools image

Releases also publish **`ghcr.io/<owner>/openshift-102-tools:<tag>`** (`Dockerfile.tools`): a UBI-based image learners run **on the cluster** so everyone shares the same CLIs without local installs. Most users paste **`deploy/openshift-102-tools-deployment.yaml`** (also in the offline tarball) into the OpenShift console **Import YAML** flow—no local `oc` required.

Included in that image:

* `oc` and `kubectl` (OpenShift stable client mirror)
* `helm` (pinned release) and `istioctl` (aligned with the Istio 1.23 workshop)
* `curl`, `wget`, `jq`, `git`, GnuPG (`gnupg2`), `skopeo`
* `/usr/local/bin/docker` — a **shim** only (no Docker Engine): `manifest inspect` uses `skopeo inspect --raw`; `pull` / `image inspect` / `history` use `skopeo` (and `jq` where needed)
* The **showroom Helm chart** tree at **`~/chart`** (symlink to `/usr/local/share/openshift-102/helm/openshift-102-workshop`), baked in at image build time so you can run **`helm upgrade --install … ~/chart`** from inside the pod without cloning this repo (see `deploy/TOOLS.md`; use **`--set tools.enabled=false`** when installing from this pod to avoid a nested tools `Deployment`).

Smoke checks: `bash scripts/verify-tools-image.sh IMAGE:TAG` (also run in CI on release). Offline layout and mirroring notes: `deploy/TOOLS.md`.

Interactive `bash` (for example from the pod **Terminal** tab after running `bash` or `bash -l`) sources `~/.bashrc`, which prints a one-time reminder of the bundled tools for this image.

== Clone and build

[source,bash]
----
git clone <repository-url>
----

[source,bash]
----
cd openshift-102-workshop
----

Clone https://github.com/shpwrck/workshop-common[workshop-common] next to this repository, then build and serve the site with the same Antora setup as the Pages workflow:

[source,bash]
----
../workshop-common/scripts/preview.sh
----

Open http://localhost:8080/index.html.

The generated site substitutes default image coordinates for the **Shared CLI tools** page in the showroom (`tools-image-basename` / `tools-image-tag` in `default-site.yml`). Point them at your registry when building disconnected documentation, for example:

[source,bash]
----
antora generate default-site.yml --stacktrace \
  --attribute tools-image-basename=ghcr.io/myorg/openshift-102-tools \
  --attribute tools-image-tag=v1.0.4
----

== Live reload (optional)

Rebuild the site whenever you save a change:

[source,bash]
----
../workshop-common/scripts/preview.sh --watch
----

== GitHub Pages

The workflow in `.github/workflows/gh-pages.yml` runs the shared Pages workflow from https://github.com/shpwrck/workshop-common[workshop-common], which publishes the `www/` output from `antora generate default-site.yml` and stamps the page footer with the release, commit, shared setup version and build time.
It builds the site for the URL GitHub Pages reports, so it works at `https://<owner>.github.io/<repo>/` or on a custom domain.

Each run also packages the Helm chart under **`helm/`** on the same site and writes **`helm/index.yaml`**, so GitHub Pages doubles as a **live Helm chart repository** (no OCI needed for `helm repo add`).

One-time: turn Pages on for this repository and choose **GitHub Actions** as the build source.

* In the GitHub UI: **Settings** → **Pages** → **Build and deployment** → **Source** → **GitHub Actions**.
* Or from a machine with the https://cli.github.com/[`gh`] CLI: `gh auth login` then `./scripts/enable-github-pages.sh` (see `scripts/enable-github-pages.sh --help`).

=== Allow `github-pages` deployments from release tags

This workflow deploys on **`main`** and on **`v*`** tags so the Helm chart version can match a release (for example **`1.0.7`** for tag **`v1.0.7`**). GitHub attaches deployments to the **`github-pages`** https://docs.github.com/en/actions/deployment/targeting-different-environments/using-environments-for-deployment[environment], which can restrict which git refs may deploy.

If a tag run fails with *Tag "v…" is not allowed to deploy to github-pages due to environment protection rules*:

. Open **Settings** → **Environments** → **github-pages**.
. Under **Deployment branches and tags**, choose **Selected branches and tags**, click **Add deployment branch or tag rule**, set **Ref type** to **Tag** and the name pattern to `v*` (or choose **No restriction** if that matches your security model).
. Re-run the failed **Publish to GitHub Pages** workflow from the **Actions** tab (**Re-run all jobs**), or push a new commit or tag after saving the environment.

With Pages enabled for your fork, replace `OWNER` and `REPO` with your GitHub `owner` and repository name (lowercase in the URL):

[source,bash]
----
helm repo add openshift-102-ghpages https://OWNER.github.io/REPO/helm
helm repo update
helm search repo openshift-102-ghpages
helm install my-workshop openshift-102-ghpages/openshift-102-workshop \
  --set image.tag=latest \
  --set image.repository=ghcr.io/OWNER/openshift-102 \
  --set tools.image.repository=ghcr.io/OWNER/openshift-102-tools
----

The chart defaults **`tools.enabled`** to **true**, which starts a second **Deployment** named like **`RELEASE-openshift-102-workshop-tools`** (Helm release name prefix) using **`ghcr.io/OWNER/openshift-102-tools`** with the same tag logic as the showroom image. Disable with **`--set tools.enabled=false`** if you only want the static site.

The chart **version** follows the Git **release tag** when the workflow runs on a **`v*`** tag (for example tag `v1.0.6` yields chart version **`1.0.6`**). Builds on **`main`** between releases use the SemVer from the latest **`v*`** tag reachable from that commit plus **`+ci.<run number>`** (for example **`1.0.6+ci.4821`**) so each Pages deploy gets a distinct chart while staying aligned with the last release line. Set `image.repository` / `image.tag` to your GHCR showroom image (often the same `v*` as the chart when you cut a release).

== Disconnected OpenShift (air-gap)

* **Helm chart:** `deploy/helm/openshift-102-workshop` — deploys the pre-built static site (UBI httpd runtime, see `Dockerfile.runtime`) and, by default, a **CLI tools** `Deployment` (`tools.enabled`, `Dockerfile.tools`) in the same namespace so learners can use **Terminal** / `oc exec` and run **Helm** from the pod (subject to ServiceAccount RBAC).
* **SBOM:** CycloneDX JSON is produced in CI for the pushed runtime image (see `.github/workflows/release-offline.yml`).
* **Release:** Push a SemVer tag `v*` (for example `v1.0.4`) or run the **Release disconnected OpenShift bundle** workflow manually. Each release publishes the Helm package, an offline tarball (`www/` + chart + `DISCONNECTED.md` + `TOOLS.md` + `openshift-102-tools-deployment.yaml` + `images-mirror.txt`), CycloneDX SBOMs for the **showroom** and **CLI tools** images, a single PDF of the hub pages and all four workshops (`openshift-102-workshops-<tag>.pdf`, built from `default-pdf-exports.yml`; the **Test PDF Build** workflow builds it without releasing), and pushes `ghcr.io/<owner>/openshift-102:<tag>` and `ghcr.io/<owner>/openshift-102-tools:<tag>`.

Details: `deploy/DISCONNECTED.md`, `deploy/TOOLS.md`.
